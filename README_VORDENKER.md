# Budget Darpan

> **AI-powered local government budget transparency and civic investigation platform for Nepal**

**Hackathon:** CodeFest 2026  
**Team:** Die Vordenker  
**Build window:** 100 hours  
**Primary platform:** Responsive bilingual web application  
**Languages:** English and Nepali  

---

## 1. Project Overview

Citizens often cannot easily understand how local government budgets are allocated, who receives public contracts, how much money has been spent, whether projects are completed, or whether official progress matches what communities experience.

Government information is commonly scattered across:

- Budget speeches
- Scanned PDF documents
- Procurement notices
- Project reports
- Municipality websites
- Financial tables
- Audit reports
- Public notices

Even when the information is technically public, it is often difficult to search, compare, verify, or understand.

**Budget Darpan** transforms these disconnected records into a searchable, bilingual civic transparency platform.

Citizens can:

- Explore local government budgets
- Follow money from allocation to project completion
- Ask questions in English, Nepali, or Romanized Nepali
- View projects on a map
- Compare allocated and spent amounts
- Read AI-generated explanations backed by source documents
- Identify unusual spending patterns
- Submit project ratings and community evidence
- Use voice input to interact with the civic investigator

The platform does not declare that corruption or fraud has occurred. It identifies **anomalies, inconsistencies, missing information, and projects that may require further review**.

## 2. Core Product Idea

Budget Darpan is not only a budget dashboard.

It is an **AI civic investigator** that connects:

```text
Budget Allocation
        ↓
Government Project
        ↓
Tender and Contractor
        ↓
Contract Amount
        ↓
Payments Released
        ↓
Project Milestones
        ↓
Official Completion Status
        ↓
Citizen Feedback and Evidence
```

This creates a public **money trail** for each government project.

### Example citizen question

> Pokhara Ward 8 ko road project ko paisa kaha gayo?

The system should return:

- Total allocated budget
- Contract amount
- Contractor information
- Amount paid
- Planned and actual timeline
- Official completion percentage
- Citizen completion rating
- Recent community evidence
- Any detected inconsistencies
- Citations to the original documents and page numbers

### 3.3 AI Civic Investigator

The investigator routes each question to the correct source.

```text
Citizen Question
        ↓
Language Detection and Normalization
        ↓
Intent Router
        ├── Exact financial question → PostgreSQL/SQLite
        ├── Document explanation → Pinecone RAG
        ├── Suspicious pattern → Anomaly Engine
        ├── Project investigation → Multiple tools
        ├── Citizen opinion → Feedback Analytics
        └── Location question → Map and Project Database
        ↓
Evidence Composer
        ↓
Bilingual Answer with Citations
```

The AI must:

- Answer in the same language as the question
- Understand English, Nepali, and Romanized Nepali
- Use exact database values for financial calculations
- Use RAG for document-based explanations
- Include source citations
- Clearly state when evidence is insufficient
- Avoid presenting suspicion as proven fraud

### 3.4 RAG System

The Retrieval-Augmented Generation system enables citizens to ask questions about uploaded government documents.

Examples:

- What did the budget speech promise about education?
- Why was this road project approved?
- What does the audit report say about capital expenditure?
- Which document mentions the contractor?
- What was the planned completion date?

#### RAG flow

```text
PDF or Document
      ↓
Text Extraction or OCR
      ↓
Page-Level Cleaning
      ↓
Chunking with Metadata
      ↓
Ollama Embeddings
      ↓
Pinecone Vector Database
      ↓
Relevant Chunk Retrieval
      ↓
Ollama Chat Model
      ↓
Answer with Source and Page Citation
```

#### Vector metadata

Each vector should include metadata similar to:

```json
{
  "document_id": "pokhara-budget-2082",
  "document_title": "Pokhara Budget Book 2082/83",
  "local_gov_code": "PKR",
  "fiscal_year": "2082/83",
  "document_type": "budget_book",
  "language": "ne",
  "page": 17,
  "section": "Infrastructure",
  "source_url": "official-source-url"
}
```

#### Vector database strategy

- **Primary:** Pinecone
- **Offline fallback:** ChromaDB
- **Embeddings:** Ollama
- **Chat model:** Ollama
- **Provider selection:** Environment variable

```env
VECTOR_DB_PROVIDER=pinecone
```

or:

```env
VECTOR_DB_PROVIDER=chroma
```

### 3.5 OCR Pipeline

The OCR pipeline processes scanned Nepali and English government documents.

#### Processing strategy

1. Detect whether the PDF already contains readable text.
2. Extract the existing text when available.
3. Use OCR only for scanned or unreadable pages.
4. Process Nepali and English using Tesseract.
5. Preserve document name, page number, municipality, fiscal year, and document type.
6. Store extracted text for review.
7. Chunk approved text.
8. Generate embeddings.
9. Store vectors in Pinecone or ChromaDB.

#### OCR tools

- PyMuPDF
- pdf2image
- Tesseract OCR
- `nep+eng` language packs
- Pillow

OCR output should not be trusted automatically. Important values should have a review status.

## 4. Mock Citizen Verification Server

For the hackathon, the team will not depend on Nagarik App or an unavailable government API.

Instead, we will build a **separate mock identity verification server**.

The mock server demonstrates how a trusted government identity provider could prevent one person from creating many accounts to manipulate project feedback.

### Verification concept

```text
Citizen Enters Phone Number and Citizenship Number
                    ↓
Mock Identity Server Matches Seeded Identity Record
                    ↓
Server Returns a Signed Verification Token
                    ↓
Budget Darpan Backend Verifies the Signature
                    ↓
Privacy-Preserving Citizen Key Is Generated
                    ↓
One Citizen Can Submit One Rating per Project
```

### Important architecture rule

The Budget Darpan backend must not trust:

```json
{
  "verified": true
}
```

when it comes directly from the browser.

Verification must come from the separate mock identity server using a signed token.

### Suggested mock identity response

```json
{
  "verified": true,
  "subject": "mock-government-identity-001",
  "phone_verified": true,
  "citizenship_verified": true,
  "municipality": "Pokhara",
  "ward": 8,
  "issued_at": 1784800000,
  "expires_at": 1784800300
}
```

### Privacy-preserving citizen key

The application should not use the citizenship number as the public or internal user ID.

```python
citizen_key = HMAC_SHA256(
    government_subject,
    CITIZEN_HASH_SECRET
)
```

Only the generated citizen key should be used to enforce uniqueness.

### Duplicate-feedback protection

The database must enforce:

```text
One verified citizen + one project = one feedback record
```

Users may edit their existing feedback, but they cannot create unlimited new ratings for the same project.

### Hackathon disclaimer

The mock verification server is a proof of architecture, not a real government identity system. Production use would require authorization, legal review, security testing, consent design, and an approved identity provider.

## 5. Authentication and User Roles

Public budget information should remain accessible without login.

### Guest

Can:

- Browse budgets
- View projects
- Use maps and charts
- Read public feedback
- Ask a limited number of AI questions
- Open source citations

### Citizen

Can:

- Submit feedback
- Rate projects
- Upload evidence
- Edit personal feedback
- Save projects
- View chat history
- Continue previous investigations

### Verified Citizen

Can:

- Receive a verified-citizen badge
- Submit one verified rating per project
- Be identified as a local resident when ward data matches
- Contribute to verified citizen aggregates

### Government Official or Data Administrator

Can:

- Upload documents
- Review OCR output
- Create and update project records
- Add tenders, contractors, payments, and milestones
- Respond to citizen concerns
- Correct extraction errors

### Moderator

Can:

- Review evidence
- Hide abusive content
- Handle reports
- Review suspicious activity
- Approve or reject public uploads

### System Administrator

Can:

- Manage users and roles
- Configure models and vector providers
- Manage source documents
- Access system logs
- Manage environment-level settings

## 9. Important Database Rules

Examples of database-level constraints:

```text
One local government + fiscal year + sector + budget type
    = one budget allocation record

One verified citizen + project
    = one feedback record

One payment belongs to one contract award

Spent amount cannot be negative

Rating must be between 1 and 5

A project must belong to a local government and fiscal year
```

Use database constraints instead of relying only on frontend validation.

## 11. Anomaly Detection

The anomaly engine identifies patterns that deserve attention.

Initial rules:

- Overspending
- Severe underspending
- Administration-heavy budget
- Very low capital spending
- Large year-over-year changes
- Repeated awards to the same contractor
- Contract amount significantly above similar projects
- Official completion inconsistent with payment or citizen evidence
- Project marked completed without a completion document
- Payment released before recorded milestone completion

### Required anomaly output

Every anomaly should include:

```json
{
  "title": "Official and citizen completion mismatch",
  "severity": "high",
  "reason": "Official completion is 95%, while verified citizen completion is 42%.",
  "data_used": [
    "official_progress_report",
    "verified_citizen_feedback"
  ],
  "threshold": "difference greater than 30 percentage points",
  "confidence": 0.81,
  "possible_explanations": [
    "Citizen reports may be outdated",
    "Only part of the project may be publicly visible"
  ],
  "recommendation": "Physical verification recommended",
  "sources": []
}
```

Never label an anomaly as proven fraud.

## 12. Source and Citation Requirements

Every AI answer based on documents should include:

- Document title
- Page number
- Section when available
- Municipality
- Fiscal year
- Source link when available
- Retrieval confidence or relevance score when useful

Example response:

```json
{
  "answer": "The budget document allocated NPR 25 million to the project.",
  "citations": [
    {
      "document": "Pokhara Budget Book 2082/83",
      "page": 42,
      "section": "Ward-Level Infrastructure",
      "source_url": "https://official-source.example/document.pdf"
    }
  ]
}
```

If the system cannot find enough evidence, it should say so directly.

## 21. API and Coding Rules

- Keep business logic out of views.
- Use services for investigation, OCR, RAG, and verification logic.
- Validate all API input.
- Add database constraints.
- Use serializers for output consistency.
- Never calculate official financial values using an LLM.
- Never trust verification values from the frontend.
- Add source metadata to every document chunk.
- Keep public and private vector data separate.
- Log sensitive actions without logging raw citizenship numbers.
- Use exact model tags.
- Keep environment-specific values in `.env`.
- Add tests for the most important demo paths.

## 22. Security and Privacy Rules

### Do

- Hash or HMAC the identity subject
- Use signed verification tokens
- Apply token expiration
- Validate uploads
- Limit file size
- Restrict document ingestion to administrators
- Use API throttling
- Add moderation status to evidence
- Hide unnecessary citizen details
- Keep an audit log for important changes

### Do not

- Store citizenship numbers in public-facing tables
- Return citizenship numbers through APIs
- Trust browser-side verification
- Put secrets in Git
- Label an anomaly as proven corruption
- Allow unrestricted public ingestion
- Store private chat history in the public RAG collection
- Use AI-generated numbers as official values

## 24. Demo Story

The demo should tell one clear story instead of showing unrelated pages.

### Recommended flow

1. Open Budget Darpan.

3. Search for a Pokhara road project.
4. Open the project on the map.

   > Pokhara Ward 8 ko road project ko paisa kaha gayo?

7. Show the AI investigator answer with citations.
8. Reveal a mismatch between official completion and citizen feedback.
9. Open citizen evidence.
10. Show the anomaly explanation.
11. Sign in using the mock verified-citizen flow.
12. Submit one project rating.
13. Attempt a duplicate submission and show that it is blocked.
14. Finish with the source documents and page references.
